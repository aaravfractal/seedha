## 2. Storage
- Statement uploads (routers/statements.py:181-195): `file.read(MAX_UPLOAD_BYTES+1)`, 10 MB cap (services/ingest.py:21), 413 `file_too_large`;
  only sha256 is stored (StatementFile, models.py:153) - bytes are never persisted. No LargeBinary/BLOB anywhere in models or migrations.
- BFF (apps/web/app/api/[...path]/route.ts): body cap 11 MB per request (lib/body.ts:8) -> upload one photo per request; streams responses
  but forwards only content-type/content-disposition (:15) - add `cache-control`, `etag` (and handle `if-none-match`) for image caching.
  `public/` prefix is already public in lib/bff.ts:17.
- Recommendation: Postgres/SQLite `LargeBinary` (bytea / BLOB) in a `site_photo` table (property_id, position, mime, bytes, sha256, width,
  height, caption_en/hi, created_at). 8 x ~200 KB = ~1.6 MB/property: trivial for Postgres, included in Railway Postgres backups (Railway
  backup features: unconfirmed), works identically on both DBs, survives redeploys, no extra Railway service. A Railway volume would add a
  second thing to back up, is not visible to the SQLite/CI path, and railway.json (deploy branch) has none today. Keep reads off hot
  paths: never load bytes in list queries (`deferred()` or separate table).
- Serving: public GET `/public/site/{slug}/photos/{photo_id}` (only for published/sample sites) through the BFF, with
  `Cache-Control: public, max-age=86400, immutable` + ETag = sha256 and versioned URLs (`?v=<sha8>`); give it its own rate bucket (8 images per
  page view would hit the 60/min "site" bucket). Owner preview of unpublished photos via owner route `/site/photos/{id}` (private, no-store).
  CSP `img-src 'self' data: blob:` (next.config.ts:12) already allows same-origin images.

## 3. Image libraries (no install)
- apps/api/.venv: Pillow 12.3.0 (transitive via reportlab 5.0.1, NOT a direct dep in pyproject.toml:10-27 or deploy's requirements.txt ->
  B1 must add `pillow` explicitly). Features: jpg (libjpeg-turbo), webp, avif = True. HEIC: not registered (only AVIF) -> cannot decode
  without pillow-heif. pyheif absent.
- `pip download` (scratch only): pillow-heif 1.8.1 wheels exist for cp312 macosx_11_0_arm64 and manylinux_2_27/2_28_x86_64; requires
  pillow>=11.1, python>=3.10. License: project BSD-3-Clause, but binary wheels state "GPLv2, due to base library licenses" (bundles libheif
  LGPLv3, libde265 LGPLv3, x265 GPLv2). Decision for lead: accept GPLv2 wheel for a server-side hackathon build, or skip HEIC (ask iPhone users
  to share as JPEG; browsers on iOS usually convert HEIC to JPEG on <input type=file accept="image/jpeg,..."> upload: unconfirmed).
- Processing recipe: open with `Image.open(BytesIO)`, check `img.format in {JPEG,PNG,WEBP,HEIF}` (do not trust content-type), set
  `Image.MAX_IMAGE_PIXELS` (e.g. 40e6) to stop decompression bombs, `ImageOps.exif_transpose(img)` FIRST, convert to RGB, `thumbnail((1024,1024))`,
  save JPEG (or WebP) with `quality` stepped down (85->60) until <= ~200 KB, passing NO `exif=`/`icc_profile` args -> re-encode drops EXIF incl. GPS.
  Test: `Image.open(out).getexif()` is empty and `"exif" not in out.info`.

- SITE_GEN_MODEL recommendation: `claude-haiku-5-5` (released 7 Oct 2026, active; text+image input; 1M ctx; adaptive thinking ON by default,
  default effort `medium`; set `output_config.effort="low"`; thinking tokens count toward max_tokens -> use ~3000, not 1000; temperature/top_p/

  [haiku-5-5/overview, migration-guide]. Whether `thinking:{type:"disabled"}` is accepted: unconfirmed. Fallback: `claude-haiku-4-5`.
- Pricing per MTok (about-claude/pricing): Haiku 5.5 (prompts <=100k) in $0.10, out $0.50, 5m cache write $0.125, cache read $0.01;
  Haiku 4.5 $1 / $5; Sonnet 5.5 and Sonnet 5 $2 / $10. Estimate one generation (8 photos @1024x768 + ~800 text tokens, ~2k out incl.
  thinking): ~9.1k in + 2k out = ~$0.002 on Haiku 5.5 (my arithmetic).
- Vision (build-with-claude/vision): image block `{"type":"image","source":{"type":"base64","media_type":...,"data":...}}`; types
  image/jpeg, image/png, image/gif, image/webp (no HEIC); max 10 MB base64 per image on Claude API, 32 MB request; 8000x8000 max; >20 images
  per request stricter dims; tokens = ceil(w/28) x ceil(h/28) (1024x768 = 1036); Haiku 5.5 is high-res tier (2576 px / 4784 tokens);
  put images before text; label "Image 1:" etc. Claude does not read image metadata.
- Prompt caching (build-with-claude/prompt-caching): `cache_control: {"type":"ephemeral"}` on a system text block; minimum cacheable
  prefix 512 tokens for Haiku 5.5 / Sonnet 5.5 / Opus 5.5 (4096 for Haiku 4.5). A <150-word system prompt (~200 tokens) alone will NOT cache
  (silently, cache_creation_input_tokens=0). Useful placement: breakpoint on the LAST IMAGE block (system+photos prefix >512) so a
  Regenerate within 5 min reads the cache; owner text after it. Usage fields: input_tokens, cache_creation_input_tokens,
  cache_read_input_tokens (total = sum), output_tokens - store all four per run.
- Structured outputs (build-with-claude/structured-outputs): `output_config.format` json_schema, Haiku 4.5/5.5 supported; NOT supported:
  minLength/maxLength, minimum/maximum, minItems>1 -> enforce 8-word captions, 3 points, 750 chars in code. additionalProperties must be false.
