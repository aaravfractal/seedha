# R3 review: performance and SEO, hotel site V2

Reviewer R3, 13 October 2026, checkout `hotel-site-v2` at `eafd3b4`. Measurements and method are in
[lighthouse.md](lighthouse.md). No product code was changed.

## Summary

- Lighthouse mobile medians for /h/deodar-view (sample hotel, no photos, 3 runs): **Performance 85,
  Accessibility 100, Best Practices 100, SEO 100**. LCP **4.05 s**, CLS **0**, TBT **89 ms**,
  FCP 2.11 s. Targets missed: Performance (90+) and LCP (< 2.5 s).
- LCP is the hero tagline (text). The time goes to critical-path bytes: 3 render-blocking CSS files
  (one is 21 KB gzip of owner-app CSS, 99.6 % unused here), 102 KB of preloaded fonts (29 KB never
  used), and 136 KB of Mukta Devanagari fonts fetched at VeryHigh priority in English. They are
  needed only for the "हि" label on the language button. Fonts are 51 % of the 470 KiB page.
- Case "with photos" was not measured: the 4-photo build was published on the API, but the web
  rebuild needed to show it was refused by the session's permission classifier (lighthouse.md).
- Globe: lazy, confirmed. None of its chunks are in the initial HTML or the Lighthouse network log.
  From the build: component `38k3wydj3u4d3.js` 2,633 B (1,466 B gzip), d3-geo
  `3glk0espggy9b.js` 22,721 B (8,678 B gzip), land-110m topology `3wfhxp7vsy6m0.js` 55,362 B
  (20,912 B gzip). Total **about 30.3 KB gzip** (gzip -9), which matches V2-GLOBE's 30.7 KB.
- SEO: title, description, canonical, Open Graph and Twitter tags are per hotel and correct. The OG
  image renders: 1200 x 630 PNG, 52.6 KB, prerendered. JSON-LD parses: one `Hotel`, with
  PostalAddress, GeoCoordinates and amenityFeature, and no `review` or `aggregateRating`. sitemap.xml
  lists 10 URLs including /h/deodar-view. robots.txt allows `/`, disallows `/api/` and names the
  sitemap. One problem: the `/api/` disallow also blocks the hotel photos (R3-4).
- Pillow 12.3.0 in apps/api/.venv supports both WebP (`True`) and AVIF (`True`).

## Findings

| ID | Severity | Where | Problem | Concrete fix |
|---|---|---|---|---|
| R3-1 | High | `apps/api/app/routers/public_site.py` `public_photo`; `apps/web/components/site/v2/HotelSiteV2.tsx` hero `<Image … sizes="100vw" unoptimized>` and `OwnerPhoto` | The brief requires responsive AVIF/WebP. Every photo is the stored JPEG (≤1024 px, up to about 200 KB, quality 85 to 60), with no `srcset`, because `unoptimized` turns off next/image. On a 412 px phone at DPR 1.75 the hero needs about 720 px. The page sends the full 1024 px JPEG (128 KB in this test) as the LCP image. At slow-4G 1.6 Mbps that is about 0.65 s of transfer for the LCP alone. With photos, LCP will be the hero image and is expected to be worse than the 4.05 s text LCP. Measured with Pillow on the test photos: 768 px AVIF q55 is 25 to 29 KB and WebP q75 23 to 46 KB, against 53 to 70 KB for JPEG q82 at the same width and 128 KB for what is served now. That is a 75 to 80 % saving on the LCP image. Encoding takes 30 to 65 ms per variant. | Smallest correct design. **API:** `GET /public/site/{slug}/photos/{id}?v=<hash>&w={480,768,1024}&fmt={avif,webp,jpeg}`. Allow only those widths and formats (anything else is a 422, so there is no unbounded cache key). Build each variant with Pillow (`thumbnail` LANCZOS, AVIF `quality=55, speed=6`, WebP `quality=75, method=4`, JPEG `quality=82, progressive`) and keep it in a small `site_photo_variant(photo_id, w, fmt, data, sha256)` table, or an in-process LRU, filled on first request. Same `Cache-Control: public, max-age=31536000, immutable` (the URL is versioned), ETag per variant, explicit `Content-Type`. Delete the variants when the photo is deleted. Explicit `fmt` in the URL avoids `Vary: Accept` and keeps CDN caching simple. **Web:** render the hero and gallery as `<picture>` with `<source type="image/avif" srcset="…&w=480&fmt=avif 480w, …768w, …1024w">`, the same for WebP, and the JPEG `<img>` fallback with `srcset`. Use `sizes="100vw"` for the hero and `(min-width:720px) 33vw, 50vw` for the gallery (already written). Keep `fetchpriority="high"` on the hero and add `<link rel="preload" as="image" imagesrcset=… imagesizes="100vw" type="image/avif">` from `generateMetadata`/the page head. Alternative: a custom next/image `loader` that builds these URLs, removing `unoptimized`. Test: format and width allow-list, sizes, cache headers, 304, and that no variant leaks across hotels (reuse `test_public_photo_route_caching_and_scope`). |

| R3-3 | High | `apps/web/components/site/v2/HotelSiteV2.tsx:326` (`हि` label), `apps/web/lib/fonts.ts` (`mukta`, root layout) | In English, the only Devanagari text on the page is the two-glyph "हि" button label. Through `--hs-text` it pulls **Mukta Devanagari 600 and 700 (67 KB + 69 KB) at VeryHigh priority**. They sit on the longest network chain (document -> CSS -> fonts). In the experiment, blocking them and the Mukta Latin fonts raised Performance from 85 to 91 and cut LCP by about 0.75 s. | Render the switch label in a system face: `.langSwitch button[lang="hi"] { font-family: "Noto Sans Devanagari", "Kohinoor Devanagari", system-ui, sans-serif; }`. Every phone ships a Devanagari system font. Mukta then loads only when the page switches to Hindi. Alternatively, subset a tiny Mukta file with only हि. Keep `preload: false`. |
| R3-4 | Medium | `apps/web/app/robots.ts` (output: `Disallow: /api/`) | Hotel photos, both on the page and in the JSON-LD `image` array, are served at `/api/public/site/<slug>/photos/<id>`. `Disallow: /api/` stops Googlebot from fetching them. The Hotel structured data then points at blocked images, and Google Images cannot index the hotel's photos. | Add `allow: ["/", "/api/public/site/"]` with `disallow: ["/api/"]`. For Google the longer, more specific Allow wins. Alternatively serve public photos from a non-/api path such as `/h/<slug>/photos/<id>`. Add a unit test on the robots output. |

Re-measure: target is that only the `24uh…` hotel CSS plus the base CSS block render. |

## Expected order of work

R3-2 and R3-3 are small CSS and layout changes that recover about 1 s of simulated LCP and bring
Performance to about 91. R3-5 brings it to about 94. R3-1 is needed so that the
with-photos page does not regress once a JPEG hero becomes the LCP element. R3-4 is a one-line
SEO fix.
